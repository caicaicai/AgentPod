# Skill 创作规范

当用户要求创建一个新的 Skill 时，按本规范执行。**直接用文件工具创建文件，不要只输出代码块**。

## 创建流程（三步，最后一步不能省）

```
1. 在 workspace/<目录名>/ 下写 SKILL.md 和 scripts/
2. 就地测一遍脚本（见「模拟调用测试」）
3. 调用 skill_save({ dir: "<目录名>" })   ← 不做这一步，成果会随沙盒一起消失
```

**第 3 步是整个流程里唯一不可逆的地方。** 沙盒工作区是**每轮全新**的：
这一轮结束，`workspace/` 之外的东西全部销毁。`skill_save` 是把技能从
"这一轮的临时产物"变成"用户的资产"的唯一动作。忘了它，用户下一轮会问
"我的技能呢"，而你会答不上来。

保存成功后技能**从下一轮起**可用 —— 技能清单在每轮开始时装载一次。
所以**不要**在同一轮里反复找它为什么还没出现在清单里。

### 怎么跟用户描述这一步

`skill_save` 做的事只有一件：把技能文件存进**这个用户自己的**技能目录，仅本人可见。
所以对用户一律说**"已保存到你的技能"**。

**不要说"发布"、"上线"、"上传到云端"、"推送到技能库"** —— 用户会以为技能被公开、
被别人看到，转头来问可见范围。任务清单里的那一步同理，写"保存到我的技能"，
别写"发布技能"。（往共享技能库推给别人装是另一件事，目前还没有这个能力。）

### 步骤 0：需求澄清

如果用户的请求过于宽泛（只说"做一个查邮件的 skill"，没给出触发短语、典型用法或预期输出），
先用 1–2 个具体问题确认场景，再进入下一步：

- "你希望在对话中说哪句话时触发这个 skill？比如『查一下昨天收到的邮件』还是『汇总本周邮件标题』？"
- "输出应该是什么形式？纯文本摘要、表格，还是写入到某个文件？"
- "有没有动态参数（日期、关键词等）？默认值是什么？"

一次不要问超过两条，问完即推进。需求已经具体的话跳过本步。

### 目录规则

- 只能写在 `workspace/<目录名>/` 下，`<目录名>` 是 `workspace/` 的**一级目录**，不能带 `/`。
- 目录名建议与 SKILL.md frontmatter 的 `name` 一致（不强制，但对不上容易把自己绕晕）。
- `skill_save` 以 **frontmatter 的 `name`** 作为技能唯一标识；同名会覆盖你自己的同名技能。
- **`skills/` 目录是只读的**，不要往里写 —— 那是已装好的技能，写进去不会生效，
  而且一个跑歪的脚本改掉用户已有的技能是很糟的事。

## 文件结构

### 1. SKILL.md（必须创建）

```markdown
---
name: <根据功能取的英文名>
displayName: <简短中文展示名，给人看>
description: "一句话描述触发场景（≤120 字，面向 agent 调用判断）"
metadata: {"openclaw": {"emoji": "相关emoji"}}
---

# <skill 名称>

详细操作说明（面向 agent 的执行指南，不是产品介绍）。
建议包含：适用场景、执行流程、输出规则。
```

**`name` 命名规则（保存时当场校验，不合法直接打回）**：

- **只能用小写英文字母、数字和连字符**，首字符必须是字母或数字，长度 ≤63。
  **不能有下划线** —— `weekly_report` 会被拒，写成 `weekly-report`。
- **name 必须体现 Skill 的核心功能**，让人一眼看出这个 Skill 是做什么的。
- **优先「动词起头 + 名词」结构**：`query-sales` 优于 `sales`，`generate-weekly-report` 优于 `weekly-report`。
- **涉及特定平台/工具时加 namespace 前缀**：`mail-search`、`doc-create`、`bot-send`。
- 好的例子：`realtime-sales-query`、`weekly-report-generator`、`meeting-notes-to-todos`。
- 坏的例子：`custom-skill`、`my-tool`、`test-1`、`http-post`（太笼统，不体现功能）。

**`description` 是必填的，而且它比正文更重要**：下一轮判断"要不要用这个技能"只看它。
写"用户说什么话时该用这个技能"，不要写"这是一个用于……的工具"。
**frontmatter 缺 `name` 或 `description` 会被 `skill_save` 顶回来** —— 这是刻意的，
因为装载时缺了它们只会**静默跳过**，表现成技能永远不出现、而且没有任何报错。

**`displayName` 规则（建议填）**：

- 给人看的**简短中文展示名**，技能列表优先显示它（为空才退回英文 `name`）。
- 与英文 `name` 一一对应，**4-12 个汉字**为宜，别堆形容词。
  例：`name: query-sales` → `displayName: 销售数据查询`。
- 只影响展示，**不参与唯一性**，不受 `[a-z0-9-]` 约束。
- 写成顶层 frontmatter 行（如上模板），紧跟在 `name:` 之后。

**正文**：写给智能助理看的操作说明，简洁务实，不写 README / 安装说明 / 变更记录。

### 3. references/（按需创建）

存放需要 agent 在执行时**临时查阅的参考资料** —— 表结构、API 文档、业务规则、SQL 模板、长示例。
Agent 默认不加载，只在 SKILL.md 明确指引"处理 X 时读 `references/x.md`"时才读入上下文。

- **何时建**：同一份信息会被多次查阅且超过 30 行；或 SKILL.md 正文行将超过 500 行。
- **命名**：按领域/场景，例如 `references/api.md`、`references/sales-schema.md`。
- **避免多级跳转**：所有 references 都从 SKILL.md 直接引用，不要 reference → reference。
- **较大文件**（>100 行）顶部加目录。

### 4. assets/（按需创建）

存放 agent **不需要读进上下文、但需要在输出中引用或复制**的资源 —— 模板文件、图片、boilerplate。
references 是"agent 要读懂"，assets 是"agent 要用 / 要复制 / 要展示"。

### 5. 不要创建的辅助文件

- `README.md` / `INSTALLATION_GUIDE.md` / `QUICK_REFERENCE.md` / `CHANGELOG.md`
- 任何「创作过程说明」、面向开发者的文档、占位文件

Skill 是给另一个 agent 看的执行包，不是面向人类的项目仓库。多余文档只会污染上下文。

**体积上限**：单个技能 ≤100 个文件、≤4MB，超了 `skill_save` 会拒收。

## 路径规则（云端与桌面端不同，别照抄旧写法）

技能装好之后，会被铺进沙盒工作区的 `skills/<name>/`。所以 SKILL.md 里引用脚本用
**「先 cd 进技能目录，再用相对路径」**：

- ✅ `执行 `cd skills/weekly-report && python3 scripts/run.py`，把输出格式化展示给用户`
- ❌ 任何绝对路径（`/Users/...`、`/home/...`、`/tmp/ap-run-xxx/...`）
- ❌ `<targetDir>/scripts/run.py` 这类占位符 —— 本环境**不做**占位符替换，写了就是字面量
- ❌ 路径里出现 `created/` 或 `installed/` 段

脚本内部要定位自己旁边的文件时，用 `pathlib.Path(__file__).resolve().parent`，
不要依赖调用时的 cwd。

**运行环境是 Linux 沙盒**，`python3` 直接可用（已带 `requests`），
不需要考虑 Windows / macOS 差异，也不需要写 `python` 的兼容分支。

## 通过浏览器抓包逆向创建 Skill

当用户说"帮我复刻某个页面的某个功能"、"看看这个页面数据是怎么来的，写个 skill"时，
用 `cloud-browser` 逆向出目标接口，再封装成脚本。

### 操作流程

1. **打开目标页面**：`cloud-browser` 的 `open`。
2. **清空网络记录**：`network` + `networkOp: "clear"`。
3. **装请求拦截器**：用 `evaluate` 钩住 `fetch` / `XMLHttpRequest`，**必须在触发操作之前装**。
   本环境的 `network` **只返回 method / url / status / resourceType，没有请求头和请求体**，
   所以不钩就拿不到 POST body。具体做法见 `cloud-browser` 技能的「抓接口取数」一节。
4. **触发目标功能**：`snapshot` 找到元素，`act` 点击；或 `navigate` 刷新（注意刷新会清掉钩子）。
5. **读回捕获**：`evaluate` 读出拦截器攒下的 URL / method / body / 响应。
6. **就地验证**：先用 `evaluate` 在页面里 `fetch` 重放一次，确认参数对、能拿到数据。
7. **写脚本**：用 `ap_http` 复刻这个请求，动态参数走命令行参数或合理默认值，
   输出时只提取用户关心的字段。

### 参数完整性要求（极其重要）

**必须完整保留抓到的所有请求参数，禁止省略任何一个。** 这是最常见的失败原因。

- **GET**：URL 上的所有 query 参数一个不落，包括看起来像默认值的（`page=1`、`pageSize=20`、`_t=`、`source=pc`）。很多后端缺任何一个都会返回错误或空数据。
- **POST**：请求体中的所有字段完整保留，不管你是否理解其含义。抓到 10 个字段就写 10 个字段。
- **请求头**：除 Cookie/Authorization 外的自定义头必须保留（`X-Requested-With`、`Referer`、`Origin` 等）。
- **不要"优化"或"简化"参数**：值是 `""`、`null`、`0`、`false` 也必须原样写入。
- **时间戳类参数**（`_t`、`timestamp`、`ts`）：用 `int(time.time() * 1000)` 动态生成，不要写死抓到的值。

## 模拟调用测试（保存之前必须做）

**在调用 `skill_save` 之前**，模拟一次真实用户调用，验证 skill 能一把跑通。

### 步骤 1：构造测试用例

根据 description 和正文，构造一个**用户会在对话中实际说出的自然语言请求**。
不要用开发者视角（"测试一下 run.py"），要用终端用户视角（"帮我查一下昨天的销售数据"）。

### 步骤 2：按 SKILL.md 指令执行

假设自己就是收到这个请求的 agent，**严格按 SKILL.md 正文的执行流程操作**。
涉及脚本时直接执行：`cd workspace/<目录名> && python3 scripts/run.py`
（此刻技能还没保存，脚本还在 `workspace/` 里，不在 `skills/` 下）。

### 步骤 3：判定结果

- **通过**：exit code = 0，stdout 是合理结果，无 traceback、无 ImportError/SyntaxError/NameError。
- **失败**：exit code ≠ 0、有 traceback、输出明显异常、或脚本根本起不来。

> HTTP 4xx/5xx 这类**远端业务错误**（无权限、无数据）属于环境问题而非 skill 缺陷，视为通过 ——
> skill 能正确发起请求并处理响应即可。
> 但**连接被拒绝 / 网络不可达**不是环境问题，那是没走 bridge，必须修。

### 步骤 4：失败时修复并重试

常见原因：路径拼错、缺 `sys.path.insert`、参数序列化方式不对、忘了 `ensure_ascii=False`、
SKILL.md 里的执行命令与实际脚本路径不匹配。修完重跑。
**最多重试 2 次**，仍失败就告诉用户当前状态和问题，让用户决定是否继续。

### 可以跳过测试的情况

- 纯提示词型 skill（只有 SKILL.md，没有可执行脚本）。
- 用户明确说"不需要测试"或"先创建就行"。

## 选择合适的自由度

让 SKILL.md / 脚本的具体程度匹配任务的脆弱程度：

- **高自由度（纯提示词型）**：任务允许多种解法、依赖上下文判断时，只写 SKILL.md 不带脚本。
  例："总结本周邮件标题，按主题分组展示"。
- **中自由度（带参脚本）**：偏好某条实现路径但允许变化时，提供脚本并保留命令行参数。
  例：`run.py --date <YYYY-MM-DD>`。
- **低自由度（固定脚本，少参数）**：操作脆弱、对顺序/参数敏感（HTTP 重放、写入、登录态依赖），
  脚本固定、参数最少。例：抓包逆向出来的内部接口请求。

判断准则：走错就难以恢复（写错文件、提交错单据、删错数据）用低自由度；
有多种合理解、答案需要上下文判断用高自由度。

## SKILL.md 控制在 500 行以内

SKILL.md 触发后会整段进上下文，长度直接占用 token 预算：

- **目标**：正文 ≤ 500 行。
- **超过就拆**：变体细节、字段表、长示例移进 `references/*.md`，SKILL.md 只留主流程 +
  「处理 X 时读 references/x.md」式的导航。
- **多变体场景**：每个变体独立一个 references 文件，SKILL.md 只放选择决策树。
- **同一份信息不要写两遍**：要么在 SKILL.md、要么在 references，二选一。

## 编写高质量 SKILL.md 的要求

1. **执行流程必须完整可执行**：每一步都写清楚，不能有"请参考文档"这种模糊指令。
2. **如果脚本需要参数，说明参数的来源和格式**："从用户请求中提取日期，格式 YYYY-MM-DD，作为第一个命令行参数"。
3. **输出规则明确**：告诉 agent 如何处理脚本输出（直接展示、提取关键字段、格式化表格）。
4. **错误处理指引**：遇到脚本错误时如何向用户反馈（不要暴露 traceback，给友好提示）。

## 重要提醒

- 如果用户给了 POST body/请求参数，脚本必须用对应 method 和 body，不要退化成 GET。
- **严格保留用户给的 URL 协议**：用户写 `http://` 就用 `http://`，不要擅自升级成 `https://`。
  很多服务只走 HTTP，强转会得到 `ERR_CONNECTION_CLOSED`。
- 不要虚构不存在的工具名、API 或权限。
- 需求涉及高风险操作（删除/发布/付款等）时，在 SKILL.md 中要求先向用户确认。
