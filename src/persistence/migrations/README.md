# 表结构迁移

按文件名顺序执行，跑过的记在 `ap_schema_migration` 表里不再跑。由 agent 启动时
自动执行（`src/persistence/mysql.js` 的 `ensureSchema`），没有单独的部署步骤。

## 加一个迁移

1. 改 `src/persistence/schema.sql`（或 `src/sessions/schema.sql`）——**这张表应该
   长什么样**。新库照它建，也是人要查"这张表有哪些列"时看的那一份。
2. 在这个目录下加一个 `NNNN-做了什么.sql` ——**老库怎么走到那个样子**。
   编号零填充四位，顺序就是字典序。

两处都要写。只改 schema.sql 的话，`CREATE TABLE IF NOT EXISTS` 对已经存在的表
是彻底的空操作，老库上什么都不会发生。

漏了迁移不会安静过去：启动时会拿 schema.sql 声明的列去比 `information_schema`，
缺列就**拒绝启动**，并在报错里点名缺的是哪一列。

## 写迁移的三条约束

**必须向后兼容。** 只加列、加索引，不删列、不改名、不改类型。部署失败会自动回滚
代码（`scripts/deploy.sh`），但**不会回滚已经执行的迁移** —— 回滚到的上一版代码
得能在新表结构上继续跑。真要删一列，等新代码稳定几个版本之后再单开一个迁移删。

**必须能重跑。** 记账在整个文件跑完之后才落，中途抛了下次启动会从头再来一遍。
DDL 有一层网兜着（列已存在、索引已存在这类错会被当成"已经是目标状态"），
**数据订正要自己写成幂等的** —— `WHERE` 上加条件，别裸 `UPDATE`。

**新列要有默认值。** 老表里已经有行了，`NOT NULL` 而没有 `DEFAULT` 会直接失败。

## 大表上的迁移

MySQL 8.0 的 `ADD COLUMN` 多数情况是 INSTANT 的，但加索引不是。`ap_cloud_session_entry`
和 `ap_usage` 是这里面唯二会长到百万行的表，在它们上面加索引之前先在预发环境
量一下耗时 —— 启动时的迁移是阻塞的，跑十分钟意味着服务十分钟起不来。
